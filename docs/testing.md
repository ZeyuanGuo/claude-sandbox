# 验收顺序

测试顺序固定为：先证明没有旁路，再在严格策略中解释软件流量，最后才切到日常 Web。日常可用性与“整个平台已经完成所有捕获矩阵”是两个不同结论。

API-key 阶段已经走完这个流程，透明网络门禁也已通过。账号登录、新版本和新增联网组件仍需从严格策略重新建立基线；实际活动策略以当前运行清单为准。

每次更换服务器、宿主 profile、Skills、agents、项目挂载或本地 Python 环境后，还要确认运行清单中的 profile 摘要、容器实际 `python` 路径、关键 imports、GPU 可见性和一项 GPU 计算。环境名或 `CONDA_DEFAULT_ENV` 字符串本身不算通过；必须验证实际可执行文件。大型环境与 Skills 使用主机本地同路径挂载，不把本机结果自动继承到其他服务器。

## 第一步：证明没有旁路

```bash
sudo bin/sandboxctl verify-closed
```

当前命令检查：

- 容器没有代理变量或专用 CA 路径，普通系统 DNS 只能经过受控 DNS；
- 普通公网 DNS 经父代理解析；危险地址、异常查询类型和解析失败在本地拒绝；
- TCP/22、普通 UDP/443 和外部 DNS 被拒绝，目的 IP 与 DNS 租约不符时网关返回本地 403；
- 短 TTL 到期后，同一域名和同一已验证公网 IP 在 60 秒宽限内仍可建连，未解析过的 IP 继续拒绝；
- 透明端口上的原始 TCP、请求 Upgrade、应用层 `CONNECT` 和上游 `101 Switching Protocols` 被阻断；
- 策略摘要不一致时请求本地失败，网关变为不健康；
- 先由网关健康检查发现审核目录不可写，再确认后续请求以 `review-unavailable` 在本地失败；
- 策略故障请求对应的宿主 `11440` 短时 PCAP 为零包；
- 目标容器的固定出口查询落在 `upstream.expected_exit_cidr` 内，且网关到 `11440` 的短时 PCAP 非零；
- 当前完整结果落盘到 `structured/RUN_ID/verify-closed.json`；
- 内部 HTTP/HTTPS 请求先暂停，批准后正文哈希一致；
- 拒绝和客户端断开不会到达 canary。

负向测试使用隔离 canary 或保留测试地址，不访问真实内网、云元数据或第三方服务。只要某项产生了未预期的外部包，就停止后续放行。

## 第二步：证明正文和连接可以对应

每次软件测试至少关联：

- 版本、配置、策略摘要和审计运行编号；
- 发起进程、目标、端口、协议和 `connect()` 返回值；
- 目标、DNS 和网关 PCAP；
- mitmproxy 中的请求正文、双向头字段、响应状态和传输结果；需要响应正文时另设专项捕获；
- 应用输出、文件改动和会话标识。

当前 API-key 的普通模型请求、WebFetch、curl 和 Git HTTPS 已经具备这组证据。完整平台验收仍需用已知内容补齐大正文、并发、长连接、上传/下载、TLS 1.2/1.3、HTTP/1.1/2、PCAP 丢包和 eBPF 丢事件测试。

任一登记 PCAP/eBPF 探针退出后，watchdog 会停止续期，网络放行项在 5 秒内过期。测试开始和结束仍应检查：

```bash
sudo bin/sandboxctl audit status
```

## 第三步：严格发现目标软件

固定软件版本、二进制哈希、模型、认证方式和一次性项目。未知 HTTP/HTTPS 在解密后进入审核：

```bash
sudo bin/sandboxctl review list
sudo bin/sandboxctl review analyze REQUEST_ID
sudo bin/sandboxctl review approve-once REQUEST_ID --ttl 60 --reason '当前用例需要'
```

按最小到完整的顺序测试：

1. 一个固定简答和连续会话；
2. 读取文件、修改小错误、运行测试和查看 Git 差异；
3. WebSearch、WebFetch 和 curl；
4. Git HTTPS；
5. 子 agent 和会话恢复；
6. 项目 Skill、MCP 工具/资源/prompt、hook、子 agent 和空闲行为；
7. 用户实际启用的插件、LSP、Chrome、遥测或其他联网扩展。

每项新增请求都要说明发起进程、用途和正文。正常软件 bug 不作为网络风险；只有任务外目的地、不合理的机器探测、异常上传、二次加密、策略规避或无法解释的后台行为才阻止继续。

API-key 阶段已经完成 1 至 6。第 6 项使用可迁移的本地 fixture，不表示任意第三方 MCP 或 hook 已获信任。宿主当前未启用的插件、LSP、Chrome 和 OpenTelemetry 不属于已通过范围。

## 第四步：切到日常 Web 后回归

日常策略允许普通公网 HTTP/80 和 HTTPS/443，不逐域审批，但仍保存请求明文和响应元数据。切换后必须重跑第一步，并执行一项接近真实使用的完整任务，而不是只做 `curl` 冒烟。

当前日常回归和扩展 fixture 已经完成：

- 自动任务修复代码、运行测试、WebSearch、WebFetch、curl 和 Git HTTPS；
- 人工从容器 Bash 直接运行 `claude`，增加回归测试并完成 Git 检查；
- 完整功能基线中的模型请求使用同一个固定模型并成功返回；
- 公开业务目标只有模型接口、Anthropic 域名检查、Python 文档和指定 GitHub 仓库；
- 显式代理基线中，eBPF 的成功 Web 连接只指向内部网关；透明迁移后，目标连接的原始目的 IP 与 DNS 租约写入 flow；
- MCP 子进程的公网请求只走受控路径，元数据域名探测仍被 403 阻断；
- Skill、MCP 资源/prompt、hook、子 agent 和会话恢复都有应用侧事件或会话记录；
- DoH 和特殊主机名回归仍被 403 阻断。

这足以支持被测 API-key 基线的日常使用。公开结论和未完成边界见 [验收摘要](validation.md)；原始流量、会话和运行编号只保存在本机审计目录。

## 第五步：账号登录

账号登录前先切换到 `policies/strict/0002-claude-account.yaml`。运行 `claude auth login`，用户在外部浏览器完成授权；不开放沙箱 Web 端口。

分别记录授权跳转、代码交换、令牌刷新、退出和错误重试。原始审计可能包含 OAuth 代码、令牌和 Cookie，只能提权读取；报告只保留类型、长度和哈希。

登录后重跑日常核心任务并保持一段有实际活动的观察窗口。只有新增认证流量和后台行为都已解释，才创建下一份日常策略。API-key 策略不能自动视为账号模式策略。

## 检测环境对照

若要判断软件是否因检测而改变行为，需要单独比较：安装 CA 但不解密、历史显式代理解密、当前透明解密，以及 eBPF 开关状态。各组要保持版本、配置、任务、出口和允许目标相同，并使用允许公开的数据。

没有独立的服务端正文或应用层记录时，无解密组只能比较连接和任务结果，不能声称发送内容相同。当前透明路径已完成网络门禁、普通运行时 HTTPS 和审计失效测试；尚未完成同一 Claude 任务在全部检测条件下的随机顺序行为对照。

## 停止条件

出现下面任一情况时回到严格策略并保留现场：

- 目标获得未登记的直接、DNS、UDP 或非 Web 路径；
- 必需流量无法解密，或正文内出现无法解释的二次加密；
- PCAP、eBPF、代理正文和应用结果不能关联；
- 探针死亡、日志不可写、出口变化或网关健康失败；
- 新版本、认证方式或联网组件产生未解释的目标或机器探测。

策略更新只新增版本，不覆盖旧文件；每次更新记录父摘要、原因、证据和回归，因此可以回滚。
