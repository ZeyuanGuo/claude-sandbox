# 存储管理

存储不足会让抓包、明文记录或容器写入中断。系统不能在证据不完整时继续联网，也不能为了本项目清理其他用户或共享 Docker 数据。

## 每台服务器的现场检查

实施前由宿主 root 对 `host.yaml` 登记的 Docker socket、根分区、审计分区和状态目录做一次只读占用检查。Docker 数据目录可能位于任意分区，不能从默认路径推断。检查结果只保存在本机，不写入发布仓库。

本项目不检查、停止或清理未登记的 Docker 服务、共享数据或其他用户内容。

## 启动条件

根分区默认保留线：

```text
max(50 GiB, 根分区容量的 5%)
```

拉取或构建镜像还要满足：

```text
当前可用空间
>= 根分区保留线
 + 新增镜像独占层
 + 构建峰值临时量
 + 容器可写层预算
```

审计分区默认保留线是 `max(200 GiB, 分区容量的 10%)`。启动前还要扣除本次运行预计产生的最大 PCAP、明文和结构化记录，不能只检查当时的 `df`。

PCAP 默认最多占 100 GiB，这是所有运行和所有抓包点的总和。明文初始上限为 50 GiB，结构化记录初始上限为 10 GiB。达到任一上限或分区保留线时先断网，不能提前删除仍在保留期内的证据。

## 只读检查

root 先确认命令操作的是登记的 Docker socket，再运行：

```bash
docker info --format '{{.DockerRootDir}} {{.Driver}} {{.LoggingDriver}}'
docker system df -v
docker ps -a --size --no-trunc
du -x -B1 --max-depth=1 /var/lib/docker /var/lib/containerd
journalctl --disk-usage
```

这些命令只生成占用报告，不能连接删除命令。`sandboxctl` 即使由 root 启动，也必须相对 `host.yaml` 中的目标用户 Home 解析用户路径，不能使用 root 的 `$HOME`。

## 清理流程

`sandboxctl storage plan` 只生成占用与候选报告。自动轮转使用独立的 `sandboxctl storage rotate`，不接收任意路径参数，也不处理 Docker 对象：

- 只遍历 `host.yaml` 登记的审计目录；
- 只删除可由运行编号或明文归档文件名确认时间、已经结束且超过保留期的对象；
- 跳过当前运行、当前 `plaintext/flows.mitm`、仍在保留期内的对象、符号链接和无法确认格式的对象；
- 通过 root-only 文件锁避免与生命周期操作同时修改审计目录。

需要人工清理时，先运行 `storage plan` 并逐项记录：

- 精确路径或 Docker ID；
- 所有者和本项目归属标记；
- 大小、用途和保留期；
- 活动容器、进程、打开文件、运行清单和报告引用；
- 删除后的恢复或重新生成方式。

允许列入人工计划的只有本项目明确拥有、已经超过保留期或可以重新生成的审计运行、专用缓存和中断临时文件。当前命令行没有通用的 `storage clean` 删除入口，避免把计划编号误当成可执行授权；需要处理自动轮转之外的对象时，必须另行确认精确路径和恢复方式。

以下内容不能自动清理：

- `docker system prune` 会涉及的未归属对象；
- 共享镜像、共享构建缓存、未登记 volume 和 Docker 数据目录内部文件；
- 其他用户的文件、进程、daemon、容器和镜像；
- 不属于本项目的当前用户文件；
- 活动数据和仍在保留期内的审计证据；
- apt 缓存、systemd journal 等系统数据。

确需处理这些内容时，先给出精确对象、收益、影响和恢复方式，再单独取得确认。
