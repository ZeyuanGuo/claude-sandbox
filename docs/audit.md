# 默认审计

目标容器启动后，宿主同时启动目标、DNS、网关三处 PCAP 和目标 cgroup eBPF。审计范围是整套受控开发机及其子进程，不按单个应用 PID，也不抓取其他用户的网络命名空间。

审计文件只能从宿主侧提权读取。目标容器不能访问、修改或删除这些证据。

## 当前记录

每次 `sandboxctl start` 生成独立运行编号，并保存：

| 记录 | 内容 |
|---|---|
| `plaintext/flows.mitm` | mitmproxy 的请求正文、双向头字段、响应状态和 flow 元数据；停止时归档 |
| `pcap/RUN_ID/target.pcap*` | 目标网络命名空间中实际出现的数据包；按主机配置循环覆盖 |
| `pcap/RUN_ID/dns.pcap*` | 受控 DNS、目标和父代理方向的数据包；按主机配置循环覆盖 |
| `pcap/RUN_ID/gateway.pcap*` | 透明网关、TLS 终止和父代理方向的数据包；按主机配置循环覆盖 |
| `structured/RUN_ID/connect.log` | 目标 cgroup 中的 `execve`、`connect`、`sendto`、`sendmsg` 调用和返回值 |
| `structured/RUN_ID/verify-closed.json` | 该运行最近一次完整封闭验收结果 |
| `runtime/dns/queries.jsonl` | DNS 查询与响应原文、地址、TTL、60 秒连接宽限、租约编号和 DoH 出口标记 |

没有形成数据包的失败直连或普通 UDP 发送会保留相应 eBPF 系统调用记录。例如无路由返回 `-101` 时，不能虚构一条 PCAP。目标和网关 PCAP 使用各自命名空间，不抓宿主主网卡。当前 eBPF 明确覆盖上述四类系统调用，不据此声称覆盖 `io_uring`、自定义内核路径或所有未来接口。

普通 TLS 被 nftables 透明送入 mitmproxy。目标的系统信任库包含网关根证书公开部分，私钥留在网关状态目录；不能解密或上游证书验证失败时关闭连接，不自动密文透传。flow 元数据同时保存原始目的 IP 和 DNS 租约编号。Claude Code、MCP Python 子进程、curl 和 Git HTTPS 的 API-key 路径已经确认可解密；透明迁移又验证了 curl、系统/Conda Python 和 Node 的系统 CA 路径。

## 明文能说明什么

完整 PCAP 不等于完整明文。当前可以读取代理处理的普通 HTTP/TLS 请求正文，以及响应头、状态和传输结果。响应正文实时转发，不写入 flow；eBPF 的主要用途是连接归属，不是 Claude Code 主程序的 TLS 明文来源。

下面情况仍可能看不到真实语义：

- 软件不信任测试 CA 或使用证书固定；
- 软件使用未适配的 TLS、QUIC 或自定义协议；
- HTTPS 正文内再次压缩、编码或加密；
- 高负载导致 PCAP 丢包、eBPF 丢事件或代理流截断；
- 新版本改变联网库或子进程。

因此，“日志没有命中可疑词”不证明没有泄露。指定软件要先用已知测试内容验证当前路径，再结合目的地、进程和任务判断。

## 严格与日常

严格和日常策略都解析普通公网域名；危险地址、异常查询类型和解析失败仍在 DNS 层拒绝。严格策略的未知 Web 请求在真实上游前暂停，操作者可以查看脱敏结构或完整原文，再拒绝或一次性批准当前哈希。

日常策略中的普通公网 HTTP/HTTPS 直接放行并写入 flow，不创建审核记录，也不等待审计分析。响应正文统一流式转发，不按域名、类型或大小枚举。当前实现没有首次域名提醒和自动待查清单；日常分析需要按运行窗口汇总 DNS、目标、进程、请求正文类型和请求量。未经规则允许的直接 IP、外部 DNS、UDP、非 Web 端口、特殊主机名和明确拒绝规则仍阻断。

API-key 功能基线中，目标业务只访问模型接口、Anthropic 域名检查、公开文档和 GitHub；对应连接都只指向内部网关。公开结论和未完成边界见 [验收摘要](validation.md)。主机运行编号、真实目标、流量数量和原始证据只保存在本机审计目录。

## 故障边界

已经实现：

- 策略摘要或请求 hook 异常时，网关本地失败；审核目录由 5 秒一次的健康检查实写检测；
- 健康检查发现审核目录不可写后会设置可恢复的存储故障，后续请求继续阻断；严重请求处理或审核结果不确定会设置永久 `audit-state-fault`，健康成功不能清除；故障到检测之间可能已有请求发出；
- mitmproxy 退出后，目标因为没有其他 Web 路径而无法联网；
- 启动审计失败时会停止容器和网络，不留下无审计运行；
- 任一登记 PCAP/eBPF 探针退出，或目标、DNS、网关进程身份改变后，watchdog 停止续期；三处 nftables 的放行项在 5 秒内过期。
- 三个长期 PCAP 分别使用 `storage.pcap_roll_size_mib` 和 `storage.pcap_roll_files` 限定循环文件大小与数量；
- 宿主通过 `/run/controlled-dev-machine-pcap/INSTANCE` 对已登记 PCAP 目录建立绑定挂载，使 `tcpdump` 在不放宽 Home 和审计目录权限的情况下写入循环文件；停止审计时卸载该路径；
- `storage rotate` 跳过当前运行，只删除本项目中已结束且超过配置保留期的 PCAP、明文归档和结构化记录；安装自动化后由 systemd 定时器执行。

尚未实现：

- 对 PCAP 丢包、eBPF 丢事件和明文流文件增长的持续自动联锁；
- 按内容识别媒体或其他二进制正文并单独删除；当前保留或删除仍以记录类型、运行编号和保留期为准。

因此运行期间要检查：

```bash
sudo bin/sandboxctl audit status
sudo bin/sandboxctl storage plan
```

`audit status` 只有五个探针/监督进程和目标、DNS、网关三个命名空间进程的 PID、启动时间、暂停状态及可执行文件路径/设备号/inode 全部匹配时才显示 `active: true`。任一审计进程死亡、磁盘不足、网关不健康或证据无法关联时，停止扩大网络并保留现场。出口租约只证明这些进程仍存活，不证明没有内核丢包、eBPF 丢事件或磁盘内容损坏。

## 数据管理

主机配置声明 PCAP、明文、结构化记录的预算、分区保留线、保留期和 PCAP 循环文件上限；`doctor` 与 `storage plan` 用预算和分区保留线做启动前检查。`storage rotate` 只处理可由运行编号或归档文件名确认时间的本项目对象：当前运行、当前 `plaintext/flows.mitm`、符号链接、异常文件名和异常目录类型一律跳过或报错。自动化安装后，定时器每 15 分钟执行一次；实际删除范围由 `host.yaml` 中的保留期决定。

自动轮转只处理上述已登记审计目录，不运行无范围的 `docker system prune`，也不删除共享镜像或其他用户文件。需要长期引用的证据必须在保留期到期前导出到独立的长期目录；自动轮转不会分析报告引用。

请求明文会包含 API key、OAuth 令牌、Cookie、项目源码和完整对话。正式报告只保存目标、类型、长度、哈希和结论，不复制秘密值。
